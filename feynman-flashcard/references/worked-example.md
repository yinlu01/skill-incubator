# 费曼自测卡 · 全程示范

以「Agent 学习 · System Prompt 实战」主题为例，演示一次完整自测怎么走。执行 skill 时对照本示例的节奏与格式。

## 第一步：出题（只给问题）

```markdown
今天的自测主题：System Prompt 实战（来自你的 Day 12 学习计划）
共 6 张卡，覆盖概念/机制/应用/辨析四层。先作答，答完一题给一题的对照。

**Q1（概念层）**：System Prompt 和 User Prompt 的本质区别是什么？

**Q2（机制层）**：为什么 System Prompt 通常要包含「角色、约束、输出格式」三件套，而不是只写一句"你是一个客服助手"？

**Q3（应用层）**：给 Code Review Agent 设计提示系统时，你会放哪些模块？为什么顺序很重要？

**Q4（机制层）**：System Prompt 是怎么被模型"记住"的？它和对话里的普通消息在技术实现上有什么不同？

**Q5（辨析层）**：System Prompt 和 Few-shot 示例，各自解决什么问题？什么时候必须用后者？

**Q6（应用层）**：你的提示系统上线后发现模型经常忽略约束条款，从提示工程角度你会依次排查哪几件事？
```

## 第二步：逐题对照（用户作答后才展示）

用户对 Q2 的作答："因为这样模型知道自己是谁、不能干什么、输出成什么样。"

```markdown
**Q2 对照**：⭕ 答对（方向对，但少了半截）

**参考答案**：三件套分别解决三类失败模式——角色（Persona）决定模型的默认语气与知识调用倾向；约束（Constraints）划红线，减少幻觉和越界行为；输出格式（如 JSON Schema、Markdown 模板）保证下游程序可解析。只写"你是客服助手"时，这三类失败全靠模型自由发挥，稳定性不可控。

**点评**：你答到了"是什么"，但费曼标准还差"为什么非这样不可"——建议补一句：每个模块对应一种失败模式，这是设计提示系统的底层逻辑。
```

用户对 Q4 的作答："呃，不知道，好像是一直放在上下文里？"

```markdown
**Q4 对照**：❌ 答错

**参考答案**：对无状态的大模型来说，System Prompt 并没有特殊的"记忆"机制——它就是每次请求都携带的第一段消息，只是通常被放在 system role 的位置，训练时模型学会了更重视它。正因为每次都要重新携带，它才稳定但会持续消耗 token；而"记住"的错觉来自服务端（如 API 层）自动拼接。理解这点就明白为什么改 System Prompt 立刻生效，而对话内容太长时它可能被"稀释"。

**点评**：这是机制层的关键盲区，3 天后重测本题。
```
